The `gecko.id` in `manifest.json` is `addons-exporter@local`, left over from the project's earlier name. It can't carry an inline comment because the manifest is strict JSON. Don't change it: Firefox uses the id to match an installed copy to its updates, so changing it breaks updates for everyone who has the extension.

## Running things

Everything below needs Node 22 or newer.

```
npm test                                   # everything
node --test tests/import.test.js           # one file
node --test --test-name-pattern="zip"      # tests whose name contains "zip"
npm run test:coverage                      # coverage of src/ (run `npm ci` once; writes coverage/index.html)
npm run lint:ext                           # Mozilla's web-ext lint
npm run clean                              # delete throwaway output
```

`npm run lint:ext` and a `web-ext` you run yourself read their ignore list from `.web-ext-config.mjs`, so tests, tooling and docs stay out of the report and out of any package.

`npm run lint:ext` finishes with 0 errors, 0 notices and 2 warnings. Both say the same thing, once for desktop and once for Android: `data_collection_permissions` is a key web-ext only expects from Firefox 140 (`KEY_FIREFOX_UNSUPPORTED_BY_MIN_VERSION`) and Firefox for Android 142 (`KEY_FIREFOX_ANDROID_UNSUPPORTED_BY_MIN_VERSION`), while `strict_min_version` is 128. The 128 floor is deliberate: it's the first version that accepts that key without an error, and an older Firefox just ignores a key it doesn't know. Raising it to 140 would only drop Firefox 128 to 139. The two warnings are expected.

`npm run clean` deletes only what this project's tools made and can make again: `node_modules`, `coverage`, `web-ext-artifacts`, Python caches, and stray `*.zip`/`*.xpi` at the project root. It never opens `.git`, `tests` or any `fixtures` folder. `npm run clean -- --dry-run` lists what it would delete.

## What the tests can and can't see

The page scripts run against a small fake DOM in `tests/helpers.js`, not a real browser, so the suite needs no dependencies. There's no CSS engine and no layout. A test can prove a script added a class or set a style, never that anything is styled, positioned or visible. The CSS side is checked as source text instead: every class the page scripts set has to be styled by some stylesheet, and the standalone report has to find the classes its script toggles in `report.css` (both in `tests/structure.test.js`).

**Checking a change by eye.** Anything that needs a real paint (an animation replaying, a colour gliding, a row fading out on search) has to be looked at once in a browser. Load the add-on as in the README, then use the page you changed. For the report, export an HTML report, open it in a new tab and try its search box and toggle. Worth doing whenever a change touches a stylesheet, `tokens.css` or a page script's visual states.

## Changing the version

The version is in `package.json` and `manifest.json`, and a test fails if they differ.

```
npm run set-version -- 1.3.0
```

Only the `"version"` line of each file changes.

## Editing the report's CSS, script or icon

The exported report is one standalone file, so its CSS, script and icon are built into it. Edit the sources, never the generated file:

- CSS: `src/background/report.css` (variables come from `src/common/tokens.css`)
- Script: `src/background/report-inline.js`
- Icon: `icons/icon32.png`

Then run `npm run build`. It regenerates `src/background/report-assets.generated.js` through `scripts/build-assets.js`, and the tests fail with a sync error until you do. After a build, regenerate the golden files with `UPDATE_GOLDEN=1 node --test tests/golden.test.js`.

## Behaviour worth knowing

- When an export finishes, the Exporter page fades out and is replaced by the confirmation page in the same tab. The background script saves the file (or the one `.zip`) through the downloads API.
- The Importer opens the first add-on as a background tab, then switches to the confirmation page right away. The background script keeps opening the rest, one after another. Links that can't be opened are skipped and the confirmation page says how many. If none open, the Importer stays and shows the error.
- AMO lookups are capped at 15 seconds each and 5 at once. A 429 is retried once after a short wait, and the exact lookup by ID is retried once after a network error, a timeout or a server error (never after a 404). After repeated failures, or 90 seconds in, the remaining add-ons skip straight to a fallback link.
- Mozilla's built-ins (`@mozilla.org`, `@mozac.org`), dictionaries and language packs are excluded: they aren't real installed add-ons and have no store listing.
- The Importer only opens `http`/`https` links.
- If every add-on in the file is already installed, the Importer shows a short note, since there's nothing to open.
